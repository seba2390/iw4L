# Black Ops 2 — fidelity ledger

Rule: Black Ops 2 matches run on Black Ops 2's own rules and data; no other
game's behaviour stands in. A rule that is not recovered is an `unknown!` in
`game_t6`, listed here with its id; `cargo xtask boundary` refuses an id that
is missing here.

Black Ops 2 ships its scripts as compiled bytecode, which IW4L does not execute.
Its matches run rules IW4L wrote for Black Ops 2 (Free for All, Team Deathmatch,
Classic zombies) on Black Ops 2's data; each such rule is listed below until it
is read from the game itself.

The compiled modules themselves are read: `fastfile_t6::scripts` takes them
out of a zone and `gsc_t6::Module` parses each one's header and tables
(includes, animation trees, code, strings, exports, imports). All 612 modules
in the eleven zombies zones of the Steam install (543 distinct names) parse,
each table ending where the next begins: 9 044 exported functions, 1.9 MB of
code (`maps/mp/zombies/_zm.gsc`: 168 functions; `_zm_perks.gsc`: 95;
`_zm_powerups.gsc`: 102).

Severity: **V** visible, **A** audible, **G** gameplay, **I** invisible.

## Open

- [ ] **G** Black Ops 2's script bytecode is not executed, so its own zombies
      rules (`maps/mp/zombies/_zm*.gsc`, the map's `zm_<map>*.gsc`) do not
      run; the rules below stand where they would. Known so far (`gsc_t6`,
      checked on every module): opcodes are one byte and the interpreter
      dispatches 124 values (`OPCODE_LIMIT`); a function starts with one of
      two entry opcodes; each import's call sites hold its kind's opcode
      (reference, call, thread call, method call, method thread call) and a
      zero byte; bit 0x10 of an import's flags marks developer-only calls.
      Every opcode's operand layout and name is known (`gsc_t6::operand`,
      `gsc_t6::Opcode`, read from each handler: how it moves the instruction
      pointer, what it pushes, the error text it raises) and every function of
      the zombies zones decodes: 748 097 instructions, each call site an
      instruction start, each string and animation reference inside an
      operand, each jump (signed 16-bit offset) landing on an instruction of
      its function, each switch on its case table and each case on an
      instruction. A function ends at its last End or Return, alignment to 4
      and four bytes; what follows is padding. WaitTillMatch's byte (the
      match count) is read by notify when the waiter wakes, not by its handler.
      `gsc_t6::Translator` puts all 9 044 functions onto the GSC IR (SafeDecTop
      drops a waittill output the script leaves unnamed, unless the frame
      marker is on top; a switch's integer case is stored as its value plus
      0x800000 in 24 bits, as the engine keys an integer selector, a string
      case as its string in the upper half, and a last case of 0 is the
      default). `t6.scripts.switch_range`: an integer selector outside
      −0x7E8000…0x7FFFFF falls to the default instead of the engine's
      `switch index %d out of range` error;
      dvar names given by hash (`dvar_hash`, djb2 of the lowercased name,
      matched on 103 names the scripts also spell out) stay hashes: the
      engine finds a dvar by hash and takes an integer as one.
      `gsc_t6::build` links modules by the loader's rules: a call or
      reference without a namespace names the builtin of that name first
      (threads never do), then a function of its module, then of each module
      it includes, in order (private functions only from their own module);
      a call may pass no more parameters than the function declares; too many
      for a builtin is reported and linked, too few or an unknown name refuses
      the scripts. Checked against the modules the running game linked:
      every builtin call site and 9 514 of 9 515 script call sites agree (the
      other links a duplicate the game kept from the map's patch zone).
      With `IW4L_T6_OWN_SCRIPTS` set (while they are brought up), a zombies
      match runs them in place of the rules below: modules, configs and tables
      from `common_zm`, `patch_zm`, `so_zclassic_<map>`, the map and
      `<map>_patch` in that order, then the captured downloaded patch
      (`t6.scripts.ffotd`); started as the engine starts a level (the map's
      `gamemode_callback_setup`, the gametype's `main`, the map's `main`, then
      `codecallback_startgametype` and `codecallback_finalizeinitialization`),
      on the map's default gametype, start location and gametype group from
      `zm/gametypestable.csv` (`t6.scripts.zm_start`). The scripts the engine
      loads itself (`codescripts/delete`, `codescripts/struct`, `_medals`,
      `_rank`, `_persistence`, `_spawning`, `maps/mp/zombies/_zm`) are loaded
      with them. Builtins are
      `sim::script::host::natives::t6`, each read from its handler; the rest
      fail as not implemented. The gametype's own zone is taken as
      `so_zclassic_<map>` whatever the gametype.
      *Needs:* the builtins.
